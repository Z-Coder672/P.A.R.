# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

P.A.R. is a website for a custom 37×18 pixel LED matrix display. Users draw pixel art (or upload/crop photos), send them to a queue, and an Arduino device polls the queue and displays each image. The Mac Mini records the camera feed for each print and uploads the recording to YouTube; the website's Latest tab embeds the most recent upload and the gallery modal embeds each print's recording.

## Repo

GitHub repo name has a **trailing dot**: `Z-Coder672/P.A.R.` Git URL is `https://github.com/Z-Coder672/P.A.R..git` (literal `.` then `.git`). `gh` CLI is not installed on this machine — use raw `git` + `curl` for repo checks.

## Running locally

```bash
php -S localhost:8000 router.php
```

`router.php` is a PHP dev-server router: it handles PHP files directly, serves static files as-is, and falls back to `index.html` for client-side routes (`/latest`, `/upload`, `/gallery`, `/about`). In production, Apache + `mod_rewrite` in `.htaccess` handles the same routing.

## Architecture

### Frontend (SPA)
`index.html` + `script.js` — a single-page app with four tabs (Latest, Upload, Gallery, About) routed via `window.history.pushState`. No build step, no framework; pure vanilla JS. The Latest tab embeds the most recent upload by reading `latest-video.php` (server-stored, written by `stream-video-id.php`). No YT Data API call from the Latest tab.

### PHP backend endpoints
| File | Method | Purpose |
|---|---|---|
| `enqueue.php` | POST | `{item: base64, name: string, artist?: string, email?: string}` → appends to `mod_queue.txt`. Optional `artist` (100-char truncate, `""` when blank) is the gallery credit line, moderated as its own check. Max 20 items (429 `queue_full`); duplicate bitmaps rejected (409 `duplicate_queue_item`); name truncated to 100 chars. Optional `email` (validated) is **never** written to the queue — it's encrypted off-webroot keyed by entry id (see Email notifications); the entry carries only `notify:true`. Rate limited → 429 `rate_limited`. |
| `next.php` | POST | Pops first item from `queue.txt`, creates `gallery/<N>/pending.json`, sets `X-Gallery-Id` header, writes `stream-pending.flag` (`{"id":N,"name":"..."}`), returns base64 bitmap (called by Arduino). Does **not** arm `snapshot-pending.flag` (the Arduino does, post-check-pass). **Must be POST**, not GET — Cloudflare/intermediates may silently retry GETs on connect-fail or 5xx, and each retry would pop another queue item the Arduino never sees. |
| `complete.php` | GET | **Redundant fallback.** Renames `gallery/<N>/pending.json` → `info.json` (`?id=N`). `snapshot-request.php` now does the same rename, so this usually no-ops. Kept because the Arduino still calls it (expects 2xx); the system no longer **depends** on it. |
| `gallery.php` | GET | JSON list of `gallery/<N>/` entries: `id`, `pending`, `bitmap`, `name`, `image` (URL to `image.jpg`/`.png` with `?v=<mtime>` cache-bust, or `null`), `video_id` (11-char YT id, or `null`). `pending` is **derived**: `true` only when still `pending.json` **and** no photo — a photo only appears post-display, so `image` forces `pending=false` even if the rename was lost. |
| `video-status.php` | GET | `?id=<videoId>` → `{exists, live, state}` via YT Data API `videos.list`. Gallery modal + Latest tab use it to skip embedding when the video is deleted or still `live` (legacy broadcast rows). |
| `snapshot-request.php` | POST | The single server-side "print done" event. Arms `snapshot-pending.flag` (auth: `X-Snapshot-Secret`) **and** finalizes the entry by renaming `pending.json` → `info.json` (idempotent). Optional `id=<N>` form param (digits-only) is the flag contents and rename target; absent/invalid id writes an empty flag and skips the rename (legacy IDless capture). |
| `snapshot-next.php` | POST | Atomically pops `snapshot-pending.flag` → `{ok, entry, id}` (`id` from flag contents, `null` for legacy/empty). Auth required. |
| `snapshot-clear.php` | POST | Unconditionally removes `snapshot-pending.flag` (auth required). |
| `stream-start.php` | POST | Atomically pops `stream-pending.flag` → `{ok, id, name}`. Flags older than 10 min are deleted and treated as empty. Auth: `SNAPSHOT_SECRET`. |
| `stream-end-set.php`, `stream-end.php` | POST | **Vestigial** — the old stop path (`stream-end.flag`). Neither the Arduino nor YT-Streamer calls them; left in place, auth: `SNAPSHOT_SECRET`. |
| `stream-video-id.php` | POST | `{id, video_id}` → merges `video_id` (11-char `[A-Za-z0-9_-]`) into `gallery/<id>/{pending,info}.json`, AND atomically rewrites `latest-video.json`. Called by YT-Streamer right after `videos.insert`. Auth: `SNAPSHOT_SECRET`. |
| `latest-video.php` | GET | `{video_id, name, id}` from `latest-video.json`, or `204` if no upload yet. No YT Data API call. Public (Latest tab fetches on every page load). |

### Bitmap format
37×18 = 666 pixels packed as bits into **84 bytes** (last byte holds 6 padding bits in its low half), transmitted as base64 (112 chars). Bit 1 = cyan (#02b2d9, "on"), bit 0 = black ("off"). Bit order within each byte is MSB-first.

### Data storage
- `queue.txt` — one JSON entry per line: `{"item":"<base64>","name":"<name>","artist":"<artist>","sub_id":"<id>"}`
- `gallery/<N>/pending.json` — `{"name":"...","artist":"...","bitmap":"<base64>","video_id":"<11-char>"?}` (`artist` is the optional credit line, `""` when omitted or on legacy entries) (present while awaiting confirmation; `video_id` added asynchronously by `stream-video-id.php`)
- `gallery/<N>/info.json` — same schema; renamed from pending.json by `snapshot-request.php` (primary) or `complete.php` (fallback), whichever fires first
- `gallery/<N>/image.jpg` (or `.png`) — real photo of the matrix displaying entry `N`, captured by YT-Streamer and uploaded in
- `snapshot-pending.flag` — exists ⇒ snapshot owed; contents = gallery id (empty for legacy captures). Written by `snapshot-request.php`, popped by `snapshot-next.php`.
- `stream-pending.flag` — exists ⇒ start a per-print recording; contents = `{"id":N,"name":"..."}`. Written by `next.php`, popped by `stream-start.php`, expires after 10 min.
- `stream-end.flag` — **vestigial**, no longer written or read.
- `latest-video.json` — `{"id":N,"video_id":"...","name":"...","ts":<unix>}` of the most recent upload. Rewritten atomically by `stream-video-id.php`; read by `latest-video.php`. The Latest tab reads only this file.
- `locks/` — file-based concurrency slots (`enqueue.N.lock`, `next.N.lock`); up to 5 concurrent requests per endpoint
- **`PRIVATE_DIR/` (ABOVE the document root, default `../par-private`, `.env`-overridable)** — everything a web client must never reach. Created 0700 on first use with its own `Require all denied` .htaccess. Contains `emails/` (encrypted addresses) and `ratelimit/` (token-bucket state). Not committed.

### Snapshot ↔ gallery flow
`next.php` pops a queue item → creates `gallery/<N>/` + `pending.json` → returns bitmap with `X-Gallery-Id: <N>`. Arduino scans, draws, runs its check (fix) pass, then POSTs `/snapshot-request.php` with `id=<N>` — which writes `snapshot-pending.flag` = `<N>` **and** renames `pending.json` → `info.json`. The Arduino then also GETs `/complete.php?id=<N>`, a redundant no-op — folding completion into the snapshot request means only one post-display call has to land, so a dropped second call can't strand a print as pending. YT-Streamer's snapshot poller hits `snapshot-next.php` every 5s, gets `{id: <N>}`, grabs a webcam frame via ffmpeg avfoundation — or, while a print is recording, copies the recorder's live JPEG sidecar (`/tmp/recordings/latest_frame.jpg`), since a USB cam allows only one opener — and uploads it to `gallery/<N>/image.jpg`. The modal renders the cyan bitmap + the real photo side-by-side, falling back to "No P.A.R. image available."

**Timing:** the flag is armed only after the check pass, and the board then sits untouched through the 10-min post-display linger — so the poller's 5s interval + ~1s grab comfortably captures the corrected board. (The old flow armed the flag in `next.php` at pop time, which let the poller photograph a mid-draw board.)

### Per-print recording flow
Every print gets its own YouTube upload titled `"<name>" printing - P.A.R.` (no timestamp). `next.php` writes `stream-pending.flag` → YT-Streamer's record orchestrator polls `stream-start.php` every `STREAM_POLL_INTERVAL`s, gets `{id,name}`, starts an **`AVFRecorder`** — native AVFoundation capture session (PyObjC, **NOT ffmpeg**, **video-only — never audio**) on the local USB webcam → `/tmp/recordings/<id>_<ts>.mov`, 1.5h hard cap, plus a throttled `AVCaptureVideoDataOutput` writing the ~1fps `latest_frame.jpg` sidecar.

**The recording stops on the snapshot signal — the unified "print done" trigger.** When the snapshot poller captures this print's snapshot (display-done) it records the gallery id + timestamp; the orchestrator sees its in-flight id match and stops. The flag is armed once per print by the Arduino's `snapshot-request.php` after the check pass, minutes into the recording. As a floor against a spuriously early signal, the stop is honored only if the signal landed ≥ `MIN_RECORD_SECONDS` (60s) into the recording. A snapshot popped with `id=null` is tied to the in-flight recording's id. **Consequence:** the recording ends at display-done, not display-done + the Arduino's 10-min linger. The 1.5h cap is the backstop if a snapshot never arrives.

On stop: `stopRecording()` finalizes the moov, then the mov goes to a background uploader thread (so the *next* print can start recording immediately) → `videos.insert` → POST `{id, video_id}` to `stream-video-id.php` → unlink the mov. Failed uploads stay in `/tmp/recordings/` for manual recovery. The gallery modal and Latest tab read `video_id` from `gallery.php`, check `video-status.php`, and embed an `<iframe>`.

The old stop path (Arduino POSTs `stream-end-set.php` → `stream-end.flag` → YT-Streamer polls `stream-end.php`) is **retired** — it could orphan a recording until the 1.5h cap if the Arduino crashed between display-done and the POST. Endpoints/flag remain but are unused; `sendStreamEnd()` was removed from the sketch.

```

SNAPSHOT_SECRET = <shared secret for snapshot endpoints>
SITE_BASE_URL = https://par.zimmzimm.com   (gallery link in notification emails)

```

Format uses ` = ` with spaces, parsed line-by-line in PHP (not `parse_ini_file()`). Keep that format when adding keys. `.env` is gitignored, so **these keys must be added to the production `.env` by hand**.

**The email-encryption key is deliberately NOT in `.env`.** It lives **above the document root** at `PRIVATE_DIR/email.key` (base64 of a 32-byte libsodium secretbox key), read by `par_email_key()` in `lib/private_store.php` — so a webroot-only exposure (`.env` served by mistake, a `/.env` scanner) can't reach it. Generate, then upload to `~/par-private/email.key` (chmod 600) via cPanel File Manager, which can reach above `public_html`:
```
php -r 'echo base64_encode(sodium_crypto_secretbox_keygen());' > email.key
```
Without a valid `email.key` enqueue still succeeds but no address is stored and no email is sent (fail-safe). Rotating the key orphans already-stored addresses.

### Email notifications (submitter "your piece is done" emails)
Opt-in via an optional email field in the upload name modal. The address is **never** written to any web-served file (`queue.txt`, `mod_queue.txt`, `gallery/<N>/*.json`) and never returned by any endpoint. It is **encrypted at rest (libsodium `crypto_secretbox`) under `PRIVATE_DIR/emails/`, above the document root**, keyed by an opaque id; only that id travels through the queue files. The key is also off-webroot (see Environment).

Lifecycle (helpers in `lib/private_store.php`):
1. `enqueue.php` → `par_store_submission_email($subId, …)` writes `emails/sub-<subId>.enc`; the `mod_queue.txt` entry gets `notify:true`.
2. `mod-action.php` approve → carries `sub_id` into the promoted `queue.txt` entry; reject → `par_delete_submission_email()`.
3. `next.php` (Arduino pickup) → `par_bind_email_to_gallery($subId, $N)` renames `sub-<subId>.enc → gid-<N>.enc`.
4. `snapshot-request.php` → `par_notify_gallery_complete($N)`: **atomically claims** `gid-<N>.enc → .sending` (so device retries and the redundant `complete.php` call can't double-send), decrypts, sends via PHP `mail()`, marks `.sent` (or restores `.enc` on failure so a retry can resend). `complete.php` calls the same idempotent hook.

The email is `multipart/alternative { text/plain, multipart/related { html, PNGs } }`, links to `SITE_BASE_URL/gallery#<id>`, and pins its envelope sender (`-f`) for SPF alignment. Below the gallery button it carries a share block: a **Submit more art** button (`/upload`), a **Text a friend** button (`sms:?&body=` — no recipient, body prefilled; that exact `?&` form is the one both iOS and Android accept), and a "Post on your socials:" row of X / Facebook / Pinterest / LinkedIn / Reddit intent links. **The logos are CID-attached inline PNGs from `media/social/`, not `data:` URIs and not hotlinked** — Gmail strips `data:` URIs and most clients block remote images by default, so CID is the only form that renders unprompted. A logo missing from disk degrades to a text link. Pinterest needs a `media` URL: `par_gallery_image_url()` uses this entry's photo, walking back up to 20 gallery ids if the (asynchronous) snapshot upload hasn't landed yet, and falls back to `favicon.webp`. Share copy lives in one place, `PAR_SHARE_BLURB`. Header-bearing values are CR/LF-stripped and the recipient re-validated at send time (header-injection defense). Delivery uses `mail()` (local Exim on Site5) — no SMTP creds in the web `.env`, and the address never leaves the web server. **Depends on the host's `mail()` working**; if Site5 mail is unreliable, swap `par_send_completion_email()` to authenticated SMTP.

### Rate limiting (`lib/ratelimit.php`)
Goal: keep request/CPU load low enough that Site5 shared hosting never flags the account. Each protected endpoint gets **two file-based token buckets** (state in `PRIVATE_DIR/ratelimit/`): a best-effort **per-IP** bucket (keyed on `CF-Connecting-IP`, since the origin only sees Cloudflare edge IPs as `REMOTE_ADDR`) *and* a **global** bucket capping total traffic to that endpoint. The global bucket is the real ban protection — it holds even if the per-IP key is spoofed by hitting the origin directly. Breach → `429` + `Retry-After`; **fails open** on any FS error (availability over strictness). Applied to `enqueue` (strict: ~5/min per IP, ~60/min global) and the polled public reads `gallery`/`queue`/`latest-video`/`video-status` (generous — tuned so the frontend's 5s gallery poll never trips; `video-status` limits also shield the YT Data API quota). **Not** applied to `next.php` or the `SNAPSHOT_SECRET`-authed endpoints, so the device/daemon can't be locked out. `lib/`, `par-private/`, and raw data files (`*.enc`, `*.flag`, `mod_queue.txt`, `pending/info.json`) are denied in `.htaccess`; `lib/*.php` also self-guard against direct requests. Red-team against a local Apache+php-fpm — php's built-in server ignores `.htaccess`.

## YT-Streamer (Python)

`YT-Streamer/YT_streamer.py` — a Mac Mini daemon that records per-print video and uploads to YouTube. Three concurrent subsystems:

1. **Record orchestrator** (`record_orchestrator`): polls `stream-start.php` for a `(gallery_id, name)`. On a hit, verifies the camera (ffmpeg enumeration), starts an `AVFRecorder` (see Per-print recording flow), waits for the snapshot-stop signal or the 1.5h cap. The recorder picks the device format of `CAMERA_VIDEO_SIZE` whose max fps ≥ `CAMERA_FRAMERATE`, **preferring `420v`/NV12 (MJPEG-backed)** — the only one that sustains 1080p30 over USB 2.0 — and pins H.264 average bitrate to `VIDEO_BITRATE`. Stop = `stopRecording()` then `stopRunning()`; the mov goes to a background uploader (`videos.insert`, `resumable=True, chunksize=8MiB`).
2. **Snapshot poller** (`poll_snapshot_queue`): polls `snapshot-next.php` every 5 s, grabs a webcam frame with ffmpeg avfoundation when idle (or copies the recorder's `latest_frame.jpg` sidecar while a recording holds the cam), uploads to `gallery/<id>/image.jpg`.
3. **Moderation poller** (`poll_mod_queue`): polls the mod queue, runs each submission through three **independent** Claude SDK calls (image, piece name, artist name) on a 3-worker pool. Auto-approve requires all three to come back high-confidence `approve`; anything else emails the human moderator. `check_artist` short-circuits a blank artist to a synthetic approve — the field is optional, so asking the model about an empty string would drag every artist-less submission into review.

YouTube auth uses OAuth 2.0 with the `youtube` scope (covers `videos.insert`). Client secrets and refresh token live in an encrypted DMG vault (`YT_streamer_vault.dmg`) protected by a Keychain-stored passphrase — see `_vault_*` and `get_youtube_service`. Auth is lazy: the vault is only mounted when the first recording arrives.

Env vars: `CAMERA_NAME` (default `Brio 100` — matched case-insensitively against the *start* of each video-device name, for both ffmpeg enumeration and the recorder's `localizedName` lookup), `CAMERA_FRAMERATE` (30), `CAMERA_VIDEO_SIZE` (`1920x1080`), `VIDEO_BITRATE` (`2500k`), `CAMERA_POLL_INTERVAL` (keeper re-scan, 15), `SNAPSHOT_SECRET`, `SNAPSHOT_REQUEST_URL`, `STREAM_{START,END,VIDEO_ID}_URL`, `STREAM_POLL_INTERVAL` (10), `SFTP_{HOST,USER,PORT}` (port 21), `SFTP_REMOTE_DIR` (chrooted; empty string valid), `SFTP_PASS_FILE` (`SFTP-pass.txt`, from the vault), plus the moderation block (`MOD_QUEUE_URL`, `MOD_ACTION_URL`, `MOD_SECRET`, SMTP creds).

```bash
cd YT-Streamer
source venv/bin/activate
python YT_streamer.py
```

**Camera is a local USB webcam, NOT RTSP** (the RTSP version is archived at `YT-Streamer/archive/`). **Recording is a native AVFoundation `AVCaptureSession` (PyObjC), NOT ffmpeg.** ffmpeg is still used for device *enumeration* and for *one-shot* snapshot stills when idle. Gotchas, do not re-litigate:
- **ffmpeg cannot record 1080p30 from this cam — that's why recording is native AVFoundation.** ffmpeg's avfoundation input only requests *uncompressed* device formats (`uyvy422`/`nv12`); uncompressed 1080p over the Brio's **USB 2.0** link caps at **~5fps** (only ≤640×480 sustains 30fps), giving a choppy recording the 30fps container hid by padding duplicate frames. The Brio's second 1080p format — `420v` (NV12, MJPEG-backed) — does a true 30fps, but ffmpeg's demuxer can't select a specific `AVCaptureDeviceFormat` (`-capture_raw_data` doesn't help). `AVCaptureSession` can (that's what Photo Booth does), so `AVFRecorder._pick_format` prefers `420v`. Verify *real* fps with `ffmpeg -i f.mov -vf mpdecimate -f null -` (unique-frame count), NOT the container's `avg_frame_rate`. The ~24fps in dim room light is auto-exposure, not the bug — the bright LED scene sits at 30.
- **No audio, ever** — the user explicitly never wants audio broadcast. `AVFRecorder` adds only a video `AVCaptureDeviceInput`. Don't add one.
- **The frame duration must be the format's exact rational.** `CMTimeMake(1, 30)` is rejected (`setActiveVideoMinFrameDuration: Not supported`) because the device advertises `1/30.00003`. `AVFRecorder` pins min/max active frame duration to the chosen range's own `minFrameDuration()`. Don't hand-construct `1/fps`.
- **The moov is finalized on `stopRecording()`, not crash-safe.** Unlike the old fragmented-mp4 ffmpeg path (which survived SIGKILL), an outright crash mid-record loses the `.mov`. The graceful-stop path always finalizes cleanly; uploads are per-print so at most one recording is at risk.
- **Bitrate must be pinned.** `AVCaptureMovieFileOutput` defaults to ~24 Mbps at 1080p → a 90-min file ≈ 16 GB. `AVFRecorder` caps it via `setOutputSettings:forConnection:` on the video connection (which only exists *after* the output is added to the session).
- **The sidecar is a second `AVCaptureVideoDataOutput` on the same session** (BGRA → CoreImage JPEG, throttled to ~1fps in the delegate) on a dispatch queue (needs `pyobjc-framework-libdispatch`). It does NOT reduce recording fps. A USB webcam allows only ONE *process* opener, so the snapshot path must NOT open the cam during a recording — it copies this sidecar (`_read_live_frame`, PIL-validated against torn reads). The orchestrator unlinks the sidecar on stop.
- **Device discovery is still ffmpeg**: `ffmpeg -f avfoundation -list_devices true -i ""` (writes to **stderr** and exits non-zero — both expected). `_refresh_camera` parses it for the device whose name starts with `CAMERA_NAME`; the keeper re-runs it every `CAMERA_POLL_INTERVAL`s whenever not recording. Enumerating doesn't open the cam (privacy LED stays off, no contention). The recorder separately re-selects by `localizedName` via `AVCaptureDeviceDiscoverySession`.
- **PyObjC is a hard dep for recording** (`pyobjc-framework-{AVFoundation,CoreMedia,Quartz,libdispatch}`), guarded on import so the rest of the daemon still runs without it. Install via `./venv/bin/python -m pip install -r requirements.txt` — **not** `./venv/bin/pip`, whose shebang points at the venv's pre-relocation home.
- **Test with `./venv/bin/python`** (system `python3` lacks `requests`/`PIL`/`pyobjc`). Importing `YT_streamer` runs the required-env check, so `.env` must be populated. Exercise the recorder directly: `from YT_streamer import AVFRecorder; r=AVFRecorder(Path('/tmp/t.mov'),'Brio',Path('/tmp/t.jpg')); r.start(); time.sleep(8); r.stop()`.

**Snapshot upload is FTPS, not SFTP, even though the env var names start with `SFTP_`.** The prefix is historical — the transport is `ftplib.FTP_TLS` (explicit TLS on port 21). Reasons, all hit during prior debugging:
- The Site5 *addon* FTP account `yt-streamer@par.zimmzimm.com` is FTP/FTPS only — SSH/SFTP on :22 only accepts the main cPanel user (`zcoder`), so paramiko-as-`yt-streamer` always gets `Authentication failed`. cPanel → FTP Accounts → *Configure FTP Client* confirms FTPS on :21.
- `SFTP_HOST` must be the Site5 origin (`shared187.accountservergroup.com`), NOT `par.zimmzimm.com`/`ftp.zimmzimm.com`. Both resolve to Cloudflare, which proxies 80/443 but does NOT tunnel 21/22 — those ports silently time out after ~60s (`Errno 60`). The HTTP endpoints in `.env` still use `par.zimmzimm.com` (443). Same origin hostname as `SMTP_HOST`.
- TLS verification is disabled (`ssl.CERT_NONE`) — the shared host presents a wildcard cert that doesn't match the origin hostname. TLS still encrypts password + data channels; only authenticity is sacrificed.
- The account is chrooted to the gallery directory, so `SFTP_REMOTE_DIR` is `""` and remote paths are bare `<id>/image.jpg`. Don't reintroduce the full `/home1/zcoder/...` path.
- The password lives in the DMG vault as `SFTP-pass.txt`, **not** in `.env`. Read lazily on the first snapshot upload via `_vault_read_sftp_password()` (same mount-then-unmount pattern as the YouTube client secret), cached in `_sftp_password_cache`. Rotate via cPanel → FTP Accounts → Change Password; update the vault file to match.
- Per `upload_snapshot()`: `mkd <id>` is best-effort — `error_perm 550` (exists) swallowed, anything else re-raised. `STOR <id>/image.jpg` is the upload; success → local mp4/jpg unlinked.

## Arduino

`Arduino Code/PARMain/PARMain.ino` — polls `POST /next.php` over HTTPS, decodes the base64 bitmap, drives the display, then polls again. Waits 10 s between polls when the queue is empty; waits 10 min after a successful display before polling again. It no longer signals the Mac Mini to stop recording — that's driven by `sendSnapshotRequest()`, the single "print done" signal; `sendStreamEnd()` was removed. WiFi credentials live in `env.h` (not committed). On-disk dir is `PARMain`.

`Arduino Code/PARMain/FLOW.md` — per-step walkthrough of boot, main loop, color classification, and GRBL streaming. **Drifts independently from the .ino** — when you change `flipDisc`, the scan offsets, servo timings, or the post-display delay, update FLOW.md in the same edit. Trust the .ino when they disagree.

`Arduino Code/PINOUT.md` — **the single source of truth for wiring**: every pin on the Nano ESP32, ServoNano, and the Mega/CNC-Shield V3, plus the ack divider, the crossed TCS3200 S2/S3 lines, power rails, and the sketches whose pin maps deviate. Same drift rule as FLOW.md — change a pin, update it in the same edit.

`Arduino Code/SerialBridge/` — USB↔Serial1 passthrough; flash to the main MCU to send raw G-code to the GRBL Mega from a PC serial monitor.

`Arduino Code/Servo*` — servo/motion bring-up & diagnosis sketches on the production D9→ServoNano path: `ServoCenter` (hold at REST, never touches GRBL — safe park during reassembly), `ServoCycle` (sustained cycling, no carriage motion), `ServoRepro` (full-board checkerboard job with logged GRBL handling — closest stand-in for a real job), `ServoYFlex`/`ServoWiggleTest` (carriage-position stress to localize an intermittent open). Diagnosed once this way: an intermittent open in the **main servo's moving-carriage cable at full +X (right) extension** — main dropped flips on the right while the witness stayed fine.

`Arduino Code/ScanBottomRowsTest/` — scan-only diagnostic over the bottom two rows (74 cells, N repeat passes, ~13 min instead of 70). Logs the raw LEDs-OFF and LEDs-ON readings **separately** plus per-frame clear min/max and `pulseIn` timeout counts — the production helper returns only the subtracted value, which cannot distinguish "ambient drifted up" from "lit came in low". Use it for any colour-sensor question; widen `ROW_A`/`ROW_B` for a full board.

`Arduino Code/ServoLoadTest/` — 5 s of servo motion / 5 s idle, repeating. No GRBL, carriage never moves. The square wave exists so a multimeter can be held on the servo feed during motion and then read the idle baseline. Use it whenever flips are inconsistent, **before** touching constants.

`Arduino Code/FlipLeftColumnTest/` — **rewritten Aug 2026 as a single-column stand-in for FlipAllTest** (`TEST_COLUMN`, 0–36), derived from it so the motion is identical by construction. ### Servo link framing (do not re-litigate)
The link is one-way with no ack, so a single dropped byte used to become a **large, valid-looking servo command**. `ServoNano.ino` did `int us = inputLine.toInt()` — `toInt()` returns `long`, `int` is 16-bit on AVR, so the truncation happened **before** the 544–2400 guard. A lost `'\n'` glued two commands together and the merged number wrapped mod 65536 into the valid window. Only merges led by `544` survive, and they always land at/past ENGAGE: `"544"+"1018"` → **1530 µs**, `"544"+"1471"` → **1983 µs**. Symptom: ~1 flip in 300–600, the arm lurches to engage instead of parking at REST, holds ~0.5 s, then rests — squisking a disc 90°. Every other corruption wraps out of range, prints `[bad …]`, and silently no-ops (looks like a missed flip). Fixes now in place, keep all three:
- `parsePulseUs()` — 3–4 chars, digits only, value kept in a `long`. Verified against all 3.45 M two-command merges: zero accepted, all 1857 legal values still accepted.
- 50 ms staleness timeout discards a stranded partial line instead of merging it forward.
- `servoTxLine()` frames with a **leading** `\n` as well as a trailing one (all 22 sketches), so the next command terminates any stranded partial. ServoNano ignores empty lines.

**A dropped command is the dangerous failure, not a corrupted one.** The parser fixes above reject bad values, but a command whose *digits* are dropped never arrives at all — nothing to reject — and the arm just holds its last position. That broke the flip arm once: a lost stage-1 REST left the arm at ENGAGE, and `flipDisc` then ran both X strokes (clear + catch, ~34 mm) with the arm buried in the board. With `"\n544\n"` framing, losing either newline is now harmless (the other terminates it), but losing any of the 3 digits still loses the command. **`SERVO_TX_REPEATS` is now 1 in every ack-equipped sketch** (PARMain, FlipAllTest, FlipAllMaskedTest, FlipLeftColumnTest, ServoCycle), and 3 only in the sketches with no ack line. Repeats were the original fix for one-way loss, but once the D2 ack went in they became *actively harmful*: 3 copies × ~6 ms of ServoNano `SoftwareSerial::recv` with interrupts off stretched a 544 µs REST pulse toward ENGAGE — the arm-breaking failure, made far more likely by the mechanism meant to prevent it. The ack (`SERVO_ACK_MODE 2`, retry-until-confirmed) replaces repeats entirely. **Don't restore `= 3` on an ack-equipped sketch.**

ServoNano correspondingly: the LED ack blink is **non-blocking** (the old inline `delay(50)` left it deaf for 50 ms right when the repeat copies arrive), and `[ok <us>]` is printed **only on a value change** — acking all three repeats triples the 9600-baud USB traffic and can back up the 64-byte TX ring, stalling the read loop. Raw per-byte echo is still on; `[bad …]` carries a running reject count.

**The link is NOT the proven culprit — measured, don't assume it.** The arm-break recurred *with* 3× repeats in place, which rules out independent per-frame loss (that would need ~8.6 % loss per frame to lose 1 command in 1600; we measured far less). Bench evidence, `ServoCycle` driving the real ENGAGE/REST1/RELEASE/REST2 sequence with the servo actually moving, both serial streams host-timestamped and correlated:

| | |
|---|---|
| commands sent | 3,034 |
| repeat frames delivered | **9,102 / 9,102 — 0.0000 % loss** |
| `[bad]` / `[stale]` frames | 0 |
| ServoNano resets | 0 |
| unacked value changes | 0 |
| send→ack latency | 20 / 32.5 / 46 ms (min/median/max), zero >100 ms |

Plus ~33 k bytes earlier with the servo stationary. **~91 k bytes total, zero dropouts.** So under bench conditions the link is essentially perfect, and the remaining suspects are things the bench does *not* reproduce: **the steppers and GRBL Mega were unpowered for every test** (stepper switching noise coupling into the D9 line, which runs along the moving carriage next to stepper cables, is the obvious untested EMI path), mechanical stall load on the arm, or the servo simply failing to return from ENGAGE — which is not a link problem at all. Rig: `ServoCycle` logs every send as `c<N> <STEP> us=<v>`; `scratchpad/analyze.py` correlates the two streams and counts how many of the 3 repeats landed per command.

**Ack line (wired 2026-07-27).** ServoNano **D3** → `[R_top]` → main-MCU **D2**, with `[R_bot]` from that junction to GND. **The rig is physically 2k/2k** (confirmed 2026-08-17; this file previously claimed 1.8k/3.3k and was wrong); the shield PCB is 2k/3.3k. The divider is mandatory — neither the RP2040 nor the ESP32-S3 is 5 V tolerant (abs max VDD+0.3 = 3.6 V on both) and the Nano header exposes the GPIO directly. The reverse direction needs nothing **in practice**, since a real ESP32-S3 output sits at ~3.25 V against the AVR's V_IH of 0.6 × Vcc = 3.0 V. **But it is not guaranteed by datasheet:** ESP32-S3 V_OH min is only 0.8 × VDD = **2.64 V**, i.e. **−0.36 V** against that V_IH. It works, and 9,102/9,102 frames were delivered on the bench with zero loss, but do not treat it as spec-compliant — if this link ever misbehaves again, a 74AHCT1G125 buffer (V_IH 2.0 V at 5 V) is the structural fix, not a resistor. D3 had to be taken off `SoftwareSerial`, which claimed it as an idle-high TX; its dummy TX moved to **D5**. Protocol is a **level, not a UART**: **idle LOW, driven HIGH** for `ACK_HOLD_MS = 40` on every accepted command (**active-HIGH since 2026-08-17** — see below). The sender already knows what it sent, so it only needs "it landed" — no baud matching and no software UART on the mbed core. The hold must **outlast the ~19 ms repeat burst** (the RP2040 has interrupts off while bit-banging and can't watch the pin during it) and stay **under the 100 ms minimum settle** so one command's ack can't be read as the next one's. **The ack is ACTIVE-HIGH, and the old "fails loud" claim was wrong.** It used to idle HIGH and pulse LOW, with the main MCU on `INPUT_PULLUP`, on the theory that a broken wire reads HIGH = "no ack". That only held for a break at the MCU pin. The divider's **bottom-leg resistor sits between that node and GND**, so a break anywhere *upstream* — the ack wire, an unplugged ServoNano, or an unpowered one — pinned the node LOW through it, which the old firmware read as **"acked"**. Every command then reported success and `SERVO_ACK_MODE 2`'s retry-until-confirmed guarantee became vacuous. No divider ratio fixes that; the polarity had to invert. Now the bottom-leg resistor *is* the fail-safe — any upstream break parks the line LOW = "no ack" = the enforced retry fires — and the main MCU uses `INPUT_PULLDOWN` for the case where the divider itself is absent.

**The ack is read as an ANALOG level, not a digital one** (`servoAckHigh()`, threshold **1.20 V**). 2k/2k puts the asserted level at 2.45–2.50 V, straddling the ESP32-S3 V_IH of 2.475 V, so `digitalRead` is a coin flip and `INPUT_PULLDOWN` drags it to 2.446 V — an outright hang under `SERVO_ACK_MODE 2`. Thresholding at 1.20 V is >1.2 V from either state (idle 0 V, asserted ≥2.45 V) and is independent of both V_IH and the divider ratio, so one firmware covers 2k/2k, 2k/3.3k and 1.8k/3.3k. `SERVO_ACK_PIN` = D2 = GPIO5 = **ADC1**_CH4 — ADC1 is mandatory, ADC2 is dead while WiFi is up. **The bottom-leg resistor parks the line LOW if ServoNano goes away** — that is the fail-safe the active-HIGH polarity relies on.

**Flash both sides together.** A ServoNano on the old active-LOW build idles HIGH, which the new main-MCU code reads as a permanent ack — the exact failure this removes. `servoAckProbeIdle()` runs at boot in all five ack-equipped sketches and logs loudly if the line idles HIGH; the reverse mismatch is not detected, so flash ServoNano *after* the main MCU.

`SERVO_ACK_MODE` in `PARMain` / `FlipAllTest` / `FlipAllMaskedTest` / `ServoCycle`: **0** = off (open-loop), **1** = observe (log every miss, keep running), **2** = enforce. **Live setting is 2**: `writeServoUs()` re-sends and **retries forever** until the ack lands, so the carriage never moves on an unconfirmed arm position. Blocking is the safe failure — every call site is reached with GRBL already idle (`flipDisc` waits for motion before each servo move; `scanGrid`'s mid-scan servo changes happen before the next move is queued), so a stall leaves the carriage stationary with nothing in flight. It deliberately **does not reset the MCU**: a reset re-homes, and homing would drag the carriage with the arm possibly still at ENGAGE — precisely how the arm broke. Miss logging is throttled (first 5, then every 100th) so a disconnected wire can't flood the log.

**Validated 2026-07-27** on `ServoCycle` (carriage immobile, Serial1 never opened): 750 commands / 187 cycles, **0 misses, 0 retries**. `servoAckWaitIdle()` doubles as a stuck-low detector — if the ack line were shorted or miswired to ground, `servoAckSeen()` would pass vacuously but every command would carry an extra ~100 ms of idle-wait. Measured step intervals were exactly nominal (300/300/100/100 ms, min = median = max), proving the line both **returns HIGH between commands and goes LOW on each ack**. Check that cadence before trusting a future ack run; inflated intervals mean the ack is being faked by a stuck-low line.

**Don't retune `SERVO_TX_BIT_US`.** Measured on the bench: at `102` the real frame is **1061.94 µs/byte** — 1.95 % *slow* (≈9417 baud), not fast, which leaves ~98 µs of margin on SoftwareSerial's pin-change re-arm. `digitalWrite` on the mbed core costs ~4.2 µs, not the ~2 µs the comment assumes. `105` already puts you at 3.8 % slow, near the tolerance limit. 33 k bytes over a motionless bench produced zero dropouts, so the trigger correlates with servo current on the 5 V/ground shared through the USB hub — not with the bit period. Bench rig: `ServoTxStress/` (RP2040, link only, no GRBL/motion; `t` prints the measured frame time) + `ServoLinkProbe/` (Nano, servo pinned at REST, parses with ServoNano's exact logic and flags merges).

- **Flip motion:** `flipDisc(x,y,catchByNextMove,inverted)` does a two-stage 180° rotation. Stage 1: servo to ENGAGE rotates the squisk 90°, then back to 0° (`SERVO_US_REST`). Stage 2: slide X by `dx` (±16.8 mm) so the arm clears the disc column, drop the arm to ~46° (`SERVO_US_RELEASE`), slide X by `−dx` — the arm catches the half-rotated squisk on the return slide and pushes it through the final 90°. Purpose: (1) LTR rows now rotate the squisk in the opposite sense, so they **unwind the column-rod twist** the RTL rows wind in instead of every row adding to it; (2) the return slide is the flip's last motion, so ending it in the sweep direction removes the 16.8 mm backtrack an LTR row used to pay before every next cell. **RTL rows keep the original flip for the same reason** — their −X return already points along the sweep. Getting this backwards (mirroring RTL instead of LTR) reintroduces the backtrack on every row. ### Lidar standoff scans — the cal-square drift correction is FICTITIOUS (do not trust it)

**ACTED ON 2026-08-20 — `LIDAR_FIT_CMM` has been re-tilted; the inverted gradient described below is FIXED.** Four full-board cadence scans (2026-08-17…20), read off the flash log, all agree the bottom sits FARTHER from the arm than the top, on 128 of 148 column-passes: +1.24 / +2.12 / +1.04 / +2.26 mm, pooled **+1.67 mm, 95% CI [+1.35, +1.98]**, where the shipped table said **−1.24 mm** (0 of 37 columns positive). It is mean-preserving, so `LIDAR_REF_MM` stays 37.69 and the per-column shape from pass 4 is untouched. Commanded RELEASE went 793–921 µs → **845–983 µs, mean 913**; row 0 is unchanged, row 17 goes 825 → 946 µs.

**Do NOT rebuild the table cell-by-cell from the daily cadence scans.** Their per-cell noise is sd 2.88 mm (SEM 1.44 mm even after averaging all four) against only 2.05 mm of real cell-to-cell structure — SNR ≈ 1. Those scans can measure a one-parameter tilt across 666 cells; they cannot measure 666 independent cells.

**WATCH THE BOTTOM TWO ROWS.** PARMain's `RELEASE_EXTRA_REACH_MM` comment records the bottom row over-rotating to ~270° at 837 µs, and it now commands 946. That observation and the 2026-08-20 lidar scans cannot both describe the same board; the scans are the newer evidence and were chosen deliberately, but this is the one place the change can go wrong, and it fails toward over-push.
`ScanColorLidarTest` samples two fixed reference squares and the analysis has historically subtracted their apparent drift from every cell. **That correction is measurably wrong.** Two full-board passes run in opposite row order (`SCAN_ROW_ORDER` 0 = top-first, 1 = bottom-first) let drift and board shape separate exactly, because the per-cell shape cancels in the pass-to-pass difference. Over 666 paired cells:

- **cell drift = 0.105 mm per pass**, 95% CI [−0.025, +0.236] — not significantly different from zero
- **the cal squares claimed +3.40 mm and +2.10 mm** on those same passes — over-reporting by 20–32×

The squares move; the cells don't. Whatever affects that fixture doesn't affect the board.

**Why it mattered so much:** the scan walks rows monotonically, one row every ~3.9 min, so **row index and elapsed time are the same variable** (measured r = 0.999987). Any error in the drift model therefore lands entirely on the vertical axis — and the 3.40 mm "correction" was 1.5× larger than the 2.31 mm vertical signal it was meant to reveal. The shipped table's vertical gradient is consequently **inverted**: it says bottom−top = −1.72 mm where the two-pass data says +0.94 mm ± 0.12. Worth ~60 µs of commanded release at the extremes.

Fixes in the sketch: `SCAN_ROW_ORDER` reverses the visit order (every loop-order decision keys off the visit index `i`, never `y`), and the cal squares are now sampled **once per row** (20 pairs instead of 3). The horizontal/per-column shape is still trustworthy — only ~0.185 mm of drift accrues within one row against a 0.921 mm horizontal sd. It is the vertical axis that is not separable from drift in a single pass.

### Reading the flash log over USB (this wasted hours twice)
- **PlogDump prints its dump ONCE**, then only re-dumps on receiving a newline. A read-only capture that attaches after that window sees **nothing at all**, which is indistinguishable from a wedged board. Send a newline periodically.
- **`Serial` is native USB CDC, so `while (!Serial)` blocks until the host raises DTR** — and `cat /dev/cu.*` never raises it (that is what separates `cu.*` from `tty.*`). Set DTR explicitly, or use a bounded wait in the sketch.
- **`arduino-cli monitor` block-buffers into a redirect** and loses the buffer when killed; `script` may not be able to allocate a pty.
- **The IDE's `serial-monitor` grabs the port back** as soon as the board re-enumerates after a flash, and silently eats the output. `pkill -f serial-monitor` immediately before capturing, not just before flashing.
- A DFU upload that fails with `LIBUSB_ERROR_PIPE` usually clears on retry; loop a few attempts.

### Display flow
Each job in `loop()`: `scanGrid()` (re-home + re-read every cell to reseed `gridState[]` after the 10-min idle) → `displayBitmap(bitmap)` → **check pass** (`scanGrid()` + `displayBitmap()` again) → `onDisplayComplete()` → `delay(10 min)`. The check pass re-scans the board after the first draw — reseeding `gridState[]` so any disc that didn't flip cleanly or was misclassified is caught — then re-runs `displayBitmap`, whose diff-against-`gridState` logic re-flips only the cells still wrong. One pass, not a loop-until-clean. Boot runs `$H` then a full `scanGrid()`.

Cell scanning uses the TCS3200 (offset `(-24.005, +8.0)` from the flip head) with an **LED ambient-subtracted read** and a **single-channel threshold on the `c` slot** — the ML classifier is retired. `readAmbientSubtracted()` averages `AMBIENT_FLASHES` (3) off/on flashes, each subtracting a 5-frame LEDs-OFF read from a 5-frame LEDs-ON read (`tcsReadRGBC` averages 5 frames), cancelling room light. `classifyDisc(c)` is then just `c < SCAN_ON_CLEAR_MAX` (**900**) → 1. That channel separates the faces by **4.9×** at the current 3V3 supply (on ~0.25k, off ~2.2k), so a fixed cut is robust. **Polarity: the sensor views the disc's BACK.** A displayed-cyan (on) disc shows its black back → reads LOW; a displayed-black (off) disc reads HIGH. `classifyDisc` returns the **FRONT/displayed** color, matching `gridState` and the target bitmap. Ambient subtraction fixed the room-lighting "blown regime" that used to garble prints.

`releaseSweep()` runs **once after `displayBitmap()`** so half-rotated discs settle before the snapshot photo. With the servo parked at `SERVO_US_REST` it does a serpentine top-to-bottom traverse — no Y-wiggle, no servo movement — routing inter-row Y travel through `moveToYSafe`. Same function in `FlipCheckerboardTest.ino`; keep them in sync.

Sanity-check the live read with `Arduino Code/ColorSensorTest/ColorSensorTest.ino` (prints ambient-subtracted RGBC + the front cyan/black result). To adjust classification, tune `SCAN_ON_CLEAR_MAX` against known ground truth — decode the target bitmap from `gallery.php` for the id in the log and compare it against that job's check-pass `px` lines; there's nothing to retrain. It is supply-dependent — see the classifier gotcha. `Arduino Code/CollectColorAmbient/` and `ScanColorAmbientTest/` log ambient-subtracted RGBC to re-check cluster separation on a new board/LED setup.

### Color Sensor ML pipeline (RETIRED)
**The ML classifier is no longer used** — all sketches classify with the single-channel threshold above. `classifier.h` / `model_weights.h` are unreferenced (left on disk); `classifier_is_blue`/`classifier_logit` are gone from every `.ino`. The PyTorch pipeline in `Color Sensor ML/` (`collect.py`, `collect_auto.py`, `train.py`, `export_header.py`, `evolve.py`, `verify_export.py`, `color_data.json`) is retained for historical reference only — you should not need it. If a future board/LED setup ever muddies the gap, **re-tune `SCAN_ON_CLEAR_MAX` rather than resurrecting the model.**

### Sketch conventions
- **Pure-Y motion only at X soft-limits.** Any vertical travel outside `flipDisc` must happen with X pinned at `0` or `-X_TRAVEL`. Use `moveToYSafe(x, y)` (emits `G0 X<limit>` → `G0 Y<targetY>` → `G0 X<targetX>`) for phase entry and any cross-row transition. Row sweeps (`scanGrid`, `displayBitmap`, `verifyAndFix`, `releaseSweep`, the `FlipCheckerboardTest` flip loop) are serpentine — end-of-row X equals start-of-next-row X, so the inter-row leg lands a pure-Y move at the limit.
- **`waitForIdle()` immediately after `$1=255`, always.** GRBL disables interrupts while committing the `$1` EEPROM write and drops Serial1 RX, so anything pipelined into that window arrives mangled and comes back as `error:2`. PARMain always had the sync; six other sketches did not, and the ESP32's faster UART turned that latent bug into a deterministic hard halt on the first job. Fixed everywhere — don't remove it.
- **G0 with one axis omitted holds that axis** in GRBL — `G0 Y<n>` is a pure-Y move at the current X. That's what lets `moveToYSafe` work without tracking gantry position.
- **Carriage moves only with the servo at REST** (except inside `flipDisc`). A naive diagonal `moveTo` across the populated board drags the arm through discs and **snapped the flip arm once** — always route cross-field travel through the X-limit edge legs.
- **Recovery from wedged comms:** `sendGcode`/`waitForIdle` carry a 60 s no-progress watchdog calling `esp_restart()` (was `NVIC_SystemReset()` on the RP2040) — match that pattern for any new long-blocking loop. `drainResponses` no longer hard-halts on GRBL faults: `ALARM` triggers `grblAlarmRecover()` (Ctrl-X soft reset → `$H` → reassert modals → clear queue → force re-scan next job), and `error:N` is retried up to 10× with 3 s spacing per same-command run before falling back to MCU reset. `errorRetryCount` resets on any clean `ok`. The queue stores text per slot (`cmdTexts[QUEUE_SIZE][MAX_CMD_LEN]`) so retries can re-send.
- **No Arduino `String` for globals.** Heap fragments over weeks of uptime. Stack-locals inside one HTTP call are fine; module-level state goes in `char[N]` (see `pendingGalleryId`).
- **Server-derived strings used in URLs/headers must be validated** before interpolation (see `isDigitsOnlyId`) — defense-in-depth if the server is ever compromised.

### GRBL gotcha (do not re-litigate)
GRBL acks (`ok`) when a line is **parsed into the planner**, not when motion finishes. To wait for motion to actually complete (e.g. before firing the servo), send `G4 P0` then `waitForIdle()` — the dwell forces a planner sync, so its `ok` is the real motion-done signal. That's what `waitForMotion()` does.

**Boot order:** when homing is required, GRBL boots into alarm state and rejects G-code with `error:9`. Always send `$H` **first**, then `G21`/`G90` after homing completes. No modal G-code before `$H`.

### Color classifier gotcha (do not re-litigate)

Classification is a single threshold on **one ambient-subtracted channel: the `c` slot of
`tcsReadRGBC`, fed from TcsFilter value 2, commanded (S2=H, S3=L)** — `c < SCAN_ON_CLEAR_MAX`
(**900**) → the cell is displaying cyan. Not a distance, not a ratio, not a model.

**Reversed 2026-08-22. The 2026-08-20 decision to threshold `b` was wrong and cost ~11× the
error rate.** Slot `b` (value 1) has *overlapping* populations — no cut separates them.
Ground truth, 666 cells of one check-pass scan against its source bitmap decoded from
`gallery.php`, best achievable errors per slot: r = 7, g = 6, **b = 14**, **c = 6**. Live on
`b` at 1112 the same scan scored **24**. Corroborated across 40 earlier jobs (ids 26–66,
26,640 cells) whose firmware thresholded `c`: 89 errors = **0.33 %**, median 2/666. On job
42 that firmware scored 0 errors while the best possible score on `b` was 17 — proof by
contradiction that `b` was never the channel being read, whatever the labels claimed.

**How to settle a channel question: decode the target bitmap from `gallery.php` for the id
in the log (`snapshot-request start id=N`) and compare it against that job's check-pass `px`
lines.** Every check pass logs all 666 cells and the board is supposed to match the target,
so every completed job is a free labelled dataset. Do this instead of reasoning from labels.

**Do NOT re-derive the mapping from a sum test** (an unfiltered channel ≈ the sum of the
filtered ones). That identity does not hold on this sensor at either supply — at 3V3 the `g`
slot reads ~5× the `c` slot, impossible for a filtered/unfiltered pair. It produced the
"S2/S3 are crossed" theory, then the 2026-08-20 reversal of it, and **both of those moved
which channel was thresholded while documenting themselves as pure relabels.** The enum
names are the datasheet table; whether they are physically right is unresolved and does not
matter.

**`SCAN_ON_CLEAR_MAX` IS SUPPLY-DEPENDENT.** The sensor moved 5 V → 3V3 on 2026-08-20, which
scaled every channel down ~3.5×. 900 is the geometric mean of the clean cluster edges at
3V3 (cyan p95 = 494, black p05 = 1651); the error count is flat at 6–7 anywhere from ~700 to
~1400, so it sits mid-plateau. Separation is **4.93×** (black p05 / cyan p95) against a
5 V-era median of 5.52× — the supply drop cost ~10 % of the margin, not the accuracy.

**Old logs are not column-comparable.** Slot semantics have changed twice; check the capture
date before comparing dumps.

Don't reintroduce squared-Euclidean distance over raw RGBC: at 20% TCS3200 scaling the
filter pulse can hit ~125 kHz, `b*b` overflows 32-bit `long`, and you get garbage. Also
don't drop the **ambient subtraction** (LED off/on): without it, room-light shifts move both
clusters and collapse the separation.


### HTTPS gotchas (do not re-litigate)
The poll path uses raw `WiFiSSLClient` with a hand-written HTTP request, not `ArduinoHttpClient`. Reasons, all hit during prior debugging:
- The server is behind Cloudflare, which always responds `Transfer-Encoding: chunked` + `Connection: keep-alive` (no `Content-Length`) over HTTP/1.1. `ArduinoHttpClient`'s chunked decoder + WiFiNINA TLS would intermittently hang on the populated-body case (status `-3` = timeout) while the trivial `"NONE"` body worked. The server responds in ~250 ms — it's a client-library issue.
- `client.stop()` must be called **after** `client.responseBody()`, not before — otherwise the body read blocks on a dead socket. Also `stop()` between requests; reusing a keep-alive `HttpClient` across GET→POST is fragile on WiFiNINA.
- The `beginRequest()`/`get()`/`sendHeader("Connection","close")`/`endRequest()` pattern returns `HTTP_ERROR_API` (-1) in our version — `startRequest()` only accepts `eIdle`. Don't retry this approach.
- The raw approach: fresh `WiFiSSLClient` per call, write the request manually with `Connection: close`, parse status/headers/body inline, decode chunked if present, then `stop()`. See `fetchNext()`.
- Always set a response timeout (or a manual timeout in the raw path) so a stuck call surfaces as an error instead of a forever-hang.
- `ArduinoHttpClient` is still imported and a global `HttpClient client` exists with `setHttpResponseTimeout(15000)` in `setup()`, but all HTTP ops bypass it — vestigial from the migration.

## Frontend gotchas

- **Pixel grid is DOM-as-state.** `.pixel.active` is the source of truth — `captureGridState()` reads it, `restoreGridFromState()` writes it. Don't add a parallel state array.
- **Call `addToHistory()` after any user-initiated pixel mutation** (draw, fill, clear, photo-import). It persists to `localStorage` and updates the undo buffer; skipping it desyncs both.
- **Modal convention:** `.upload-modal.hidden` toggles visibility, backdrop click dismisses, action buttons use `.queue-modal-confirm` / `.queue-modal-cancel` (or a red destructive variant like `.clear-modal-confirm`).
- **Font Awesome 6.7 is loaded site-wide** via the CDN link in `index.html`. Use `<i class="fa-solid fa-..."></i>` inline; no setup needed.
- **Gallery cards capture `item` in a click-handler closure** at render time (`loadGallery`). If the entry goes pending → completed server-side, the cached `item.pending` stays `true` until cards re-render. Fix is two-pronged: `openGalleryItem` re-fetches `gallery.php` on click and resolves the latest entry by id; plus `startGalleryPolling` re-runs `loadGallery({ silent: true })` every 5s while the gallery tab is active.
- **Modal renders bitmap + name unconditionally**, then layers status (pending / snapshot photo / "No image available") on top. Don't reintroduce branches that hide the bitmap during pending — the bitmap is in `pending.json` from the moment `next.php` fires.
- **`gallery.php` rename TOCTOU race:** there's a small window where `gallery.php` sees `pending.json` exists, then `file_get_contents` returns `false` because the rename just landed. The endpoint silently `continue`s past such entries, so a single fetch can briefly miss an item mid-transition. The 5s polling masks this.
- **Gallery deep-links via `#<id>` hash.** A hash of a bare gallery id (e.g. `/gallery#129`, or a bare `/#129` — normalized via `replaceState`) switches to the Gallery tab and opens that entry's modal on load and on `hashchange` (`galleryIdFromHash()` + `openGalleryItemById()`). Opening any modal writes `/gallery#<id>` (shareable/refresh-safe); closing strips the hash. The completion email's "View it in the gallery" link uses this (`par_send_completion_email($to,$name,$galleryId)` appends `#<id>`). Hash regex is digits-only.
- **Adding a new SPA tab** takes three edits: nav link `<a data-tab="X">` in `index.html`, `<section id="X" class="tab-content">` in `index.html`, and an `if (pathname === '/X') return 'X';` branch in `getActiveTabFromUrl()`. No server changes.
- **`.tab-content.active` is flex-row by default** — sibling children sit side-by-side. Add `#tabid.tab-content.active { flex-direction: column; }` for stacked content (latest and about already do this).
- **`loadLatestRecording()` clears `.latest-container.innerHTML`** on every load. Static content for the latest tab must be a *sibling* of `.latest-container`, not a child.
- **In-page links to other tabs** should use `class="nav-link" data-tab="X"` so the existing `navLinks.forEach` handler routes them via `pushState`. They must exist at script load time (the handler captures `navLinks` once).
- **Don't move gallery-entry creation to `enqueue.php`.** Tried once so the bitmap would appear in the gallery at upload time; user pushed back — the bitmap should be visible only once the Arduino picks the item up. Keep entry creation in `next.php`.
